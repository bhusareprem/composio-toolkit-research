100 apps, one question: can an agent call this today?

A research agent crawled, searched and browsed 100 real apps requested by customers to find out whether each one could become an agent toolkit right now — and if not, exactly what's in the way. Below: the patterns first, then the full evidence table, then the honest accounting of what the agent got wrong and how that was caught.

The patterns (read this, skip the rest if you're busy)

Seven findings that came out of clustering all 100 rows — this is the point of the exercise, not the table itself.

70/100 already in Composio's catalog

Cross-checked against Composio's own public toolkit list — the real number that matters

docs.composio.dev/toolkits publicly lists all ~1,561 toolkit slugs Composio already ships, no account required. Matching all 100 apps against it: 70 already exist. The other 30 are the actual net-new opportunity list — see the dedicated section below, ranked by how buildable each one is.

Dev/Infra & Productivity: 20/20

The easiest categories are a landslide

Every single developer-infrastructure app (GitHub, Vercel, Cloudflare, Supabase...) and every productivity/PM app (Notion, Linear, Asana...) is buildable today with zero blockers. These are companies competing for developer mindshare — self-serve API access is table stakes for them.

Finance/Fintech: 3/10 clean

The hardest category, by far

Half of Finance/Fintech apps are blocked outright. The split is sharp: accounting & crypto tools (Stripe, QuickBooks, Xero, Binance) are wide open; corporate-card fintechs (Brex, Ramp) and data vendors (PitchBook, DealCloud) require you to already be a paying customer before any credentials exist.

API key > OAuth2

The plurality auth method isn't what you'd guess

Across 146 auth-method mentions (many apps support more than one), plain API key / Bearer token schemes (75) actually edge out OAuth2 (59). OAuth2 dominates mindshare; simple tokens dominate the actual dataset — and are usually faster to build against.

39/100 already have an MCP

The green field is smaller than it looks

Roughly two in five apps already show some official, community, or vendor-claimed MCP server. Stripe, GitHub, Notion, Airtable, Linear, Apify, Firecrawl and Reducto shipped their own. The "build the first toolkit" opportunity is concentrated in the other 61.

18/30 blocked apps: a gate, not a wall

The dominant blocker is friction after signup, not missing tech

Of the 30 apps that aren't cleanly buildable, 18 have a real API and a real signup flow — they just add an app review (Google/Meta/Pinterest), a use-case review (Plaid), or require you to already be a paying customer (Brex, Ramp, Devin) before it's usable. Only a minority are truly closed-door, contact-sales products.

2 apps genuinely won the fight

Paygent Connect and iPayX defeated the research

No independently verifiable public docs could be found for either, even after crawling, searching and manually browsing. Both are flagged honestly as unresolved rather than guessed at — see the Honesty section below.

Buildability by category

Green = buildable today, no blockers. Amber = buildable with real friction (a review gate, a paid plan, a non-standard auth scheme). Red = not buildable without a sales conversation or an existing paid relationship.

The real opportunity list: 30 apps not yet in Composio's catalog

Cross-referenced all 100 hint URLs against docs.composio.dev/toolkits — a public page listing every toolkit slug Composio currently ships (~1,561 of them), no API key needed. 70 of the 100 researched apps are already there. These 30 aren't, ranked by how buildable each one is today — this is the list worth taking to an engineering backlog.

The agent: what actually did the research

A four-stage pipeline. The crawler and the structured extraction are automated and re-runnable; two stages needed a human (or a real browser) because the crawler alone got fooled.

STAGE 1

Crawl fetch_docs.py

Python + requests + BeautifulSoup hits all 100 hint URLs, strips boilerplate, saves cleaned text. Logs every status code and failure — a 403 is a finding, not a null.

But docs.composio.dev/toolkits is a public page listing all ~1,561 toolkit slugs with no auth at all — scraped and matched against all 100 apps by name/slug. 70 hits, 30 misses.

STAGE 4

Extraction & targeted search

Claude (this session) read every crawled file and, for ~20 apps where the crawl was too thin or ambiguous (niche fintechs, brand-new AI tools, apps behind bot-detection), ran targeted web searches to confirm auth model and access tier before writing the structured verdict.

Human-in-the-loop
→
STAGE 5

Browser verification

A real browser session (not the plain-HTTP crawler) re-visited 10 sampled apps' actual docs pages by hand, catching 2 real misses and 3 minor corrections — folded back into the shipped dataset.

Human-in-the-loop

Why extraction wasn't a fully unattended script: this machine had no spare Gemini/Anthropic API key to wire into an unattended extraction step. Rather than skip Composio's own resources entirely, stage 3 uses the one Composio surface that's genuinely public — the toolkit list docs.composio.dev serves to render its own docs site — instead of the authenticated API, which would have needed an account created on the user's behalf (a deliberate line not crossed; see the Honesty section). The reasoning in stage 4 was Claude, directly, inside this research session, reading real crawled text and real search results rather than working from memory. Stages 1, 2 and 3 are fully scripted and re-runnable by anyone with Python; the README explains how to wire in your own LLM key to make stage 4 unattended too.

Honesty: where this fell short

Said plainly, per the assignment's own rule — an app defeating the research is a correct finding, not a failure to hide.

  • Paygent Connect and iPayX have no independently verifiable public API documentation. Paygent Connect's own hint ("NMI-powered") couldn't be matched to a specific product — the closest real match, a Japanese payment gateway called Paygent, is entirely enterprise/sales-led with no visible connection to NMI. iPayX turned out to be real and unusually agent-forward (its homepage advertises native MCP support) but publishes no reference docs. Both are marked buildability: no with low/medium confidence rather than guessed at.
  • Meta's developer domain (developers.facebook.com) blocked our crawler outright — every path returned HTTP 400 regardless of URL, for WhatsApp Business, Meta Ads and Threads alike. Those three entries are backed by prior knowledge and search confirmation, not a successful crawl, and are flagged accordingly.
  • We did not create a Composio account to query the authenticated toolkit API (backend.composio.dev/api/v3), which would give richer per-toolkit metadata than the public docs page (exact auth schemes, tool counts, trigger support). We used the public, unauthenticated docs.composio.dev/toolkits listing instead — enough to answer "does a toolkit already exist," not enough to fully replace the authenticated source. Creating accounts on the user's behalf is outside what this agent will do unprompted, and that gate is itself a small data point about what "self-serve" means in practice, even for Composio's own product.
  • The name-matching against Composio's catalog is heuristic (slug normalization + a manual alias table for tricky names like "Lark" vs "Feishu"), not a guaranteed-exact match. A handful of the 30 "net-new" apps could in principle exist under a slug this pass didn't try — worth a second look before treating the opportunity list as final.
  • Verification covered 10 of 100 apps, not all 100 — a deliberate scope choice under a time budget. See the accuracy caveat in the Verification section above for what that implies about the other 90.
  • Podio, Front, and systeme.io are marked buildable but flagged with softer notes (aging docs, plan-gated scopes, narrow surface respectively) — a "yes" that still deserves a second look before committing engineering time.
